# Windows tracing — перша ізольована зміна в пакеті

## Статус

Перенесено перевірений контрольований експеримент у пакет і додано експорт
спостережень JSON v1. **Це ще не універсальний `surgery scan -- python main.py`
і не готове з'єднання з inventory.** Поточний `surgery inventory` не змінено.

Модуль запускає відомий власний дочірній код з одним нативним читанням файла.
ETW-сесія починається до запуску дитини; батько незалежно отримує час її
створення. Дитина отримує DOS/NT-шляхи та файловий ID з handle до й після
читання. Це контрольні докази для перевірки, не універсальні можливості ETW.

Inventory, CLI, README та pyproject.toml у цій зміні не редагуються. Немає
видалення залежностей, повторної інвентаризації, нового venv, прихованих
завантажень, телеметрії, власних драйверів/служб чи потреби в компіляторі.
Використовуються стандартна бібліотека і штатні Windows logman/tracerpt.

## Запуск з кореня репозиторію

PowerShell **від адміністратора**, той самий Python для обох команд:

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
python -m pip_surgery.windows_tracing
```

Скопіюйте фактичну папку з рядка `Probe folder:`. Потім:

```powershell
python -m pip_surgery.windows_tracing_inspect "<фактична папка запису>"
```

Кутові дужки — лише позначення, їх вводити не потрібно. Якщо пакет вже
встановлений з цього коду, PYTHONPATH не потрібний. Новий entry point не
додається. Наявне налаштування src discovery включає Python-модулі; збирання
wheel цим патчем окремо не перевірене.

Збір короткочасно **системний** для вибраних провайдерів, не відфільтрований
на вході до дитини. Логи можуть містити сторонні шляхи та назви процесів.
ETL/XML/raw JSON залишайте локально. Автоматичного редагування приватних
даних немає. Підвищена дитина тут — відомий тест, не рекомендація запускати
довільну користувацьку програму з підвищенням прав.

Без підвищення перевірена конфігурація повертала 0x80070005; із підвищенням
працювала. Альтернативні делеговані права ETW не перевірялися.

## Результати

Папка `etw-probes/pip-surgery-combined-<capture_id>/` містить:

- `report.json`: контрольні докази, Windows/Python/права, помилки запуску,
  код дитини, стан зупинки; це НЕ observation schema v1.
- `trace.etl`, `providers.txt`: початковий запис і параметри провайдерів.
- `decoded.xml`, `trace-summary.txt`: результати tracerpt.
- `combined-inspection.json`: перевірки одного контрольного ланцюжка.
- `raw-kernel-records.jsonl`: записи обох провайдерів з raw XML та ID доказів.
- `observation.json`: погоджена консервативна структура спостережень v1.

Кожний Kernel-File запис має подію у observation.json. Невідомі операції та
події без шляхів/PID не відкидаються. Інші провайдери лишаються в ETL/XML;
процесні докази також є в raw-kernel-records.jsonl.

Повторна інспекція перезаписує лише похідні результати цієї папки. ETL та
report.json не змінюються. Папки не видаляються автоматично. Якщо декодування
не вдалося, report.json/ETL залишаються доказами: відсутній observation.json
не можна вважати коректним порожнім записом.

## JSON v1

Версія стосується спостережень, а не inventory schema_version 1.

Верхній рівень: schema_version, capture_id, environment, backend, started_at,
finished_at, scope, recording_stopped_cleanly, postprocessing_completed,
losses, analysis_readiness, warnings, errors, counts, evidence, events.

Подія: event_id, capture_id, scenario, pid, process_identity,
process_attribution, operation, raw_path, normalized_path, path_resolution,
correlated_path_candidate, success, timestamp, timestamp_raw, source, evidence.

- raw_path — лише FileName власної події. Для Read без FileName це null.
- normalized_path — null до перевірки inventory-адаптера. Поля path немає.
- Шлях з Create для контрольного Read — окремий correlated_path_candidate
  з capture_id та ID доказу, не підміна початкового шляху.
- PID та process_identity заповнюються лише для вибраних подій, що пройшли
  контрольні перевірки. Для інших — null; PID заголовка збережений у доказі,
  але не видається за перевіреного виконавця.
- Unknown тип/версія зберігається з operation=unknown.
- success=null: зіставлення OperationEnd тут не реалізоване.
- timestamp_raw незмінний; timestamp=null. Offset не виправляється.
- Час створення процесу — рядок цілого FILETIME, 100-нс інтервали від
  1601-01-01T00:00:00Z. Sequence number не вважається глобальним постійним ID.
- Часи runner — ISO 8601 UTC; це не точні моменти першої/останньої ETW-події.
- Обидві ознаки analysis_readiness залишаються false, навіть якщо контрольний
  ланцюжок пройшов. Майбутня придатність до планування виключень не є дозволом
  видаляти: потрібні правила захисту та перевірки програми.
- Невизначені дані не можна прибрати й позначити решту файлів невикористаними.

FileObject/Irp — повторно використовувані адреси, не сталі файлові ID.
FileKey не прирівнюється до файлового ID з handle. Інспектор відхиляє
неоднозначні/повторні Read, а не прикидається загальним корелятором.
Відносний порядок перевіряється через час заголовків з однаковим серіалізованим
offset, не через позицію в XML. Це ще не доказ коректного абсолютного часу.

tracerpt_total_events_lost=0 — лише значення повідомленого лічильника ETW.
buffers_lost=null означає невиміряні дані. Нуль не доводить повного покриття.

## Що реально перевірено раніше

Ручні запуски окремих попередніх скриптів: Windows 11 build 26200 x64,
Python 3.14.5, MinGW GCC UCRT 16.1.0 x64. Нові пакетні команди й exporter
потребують окремого Windows-перезапуску. Windows 10, інші збірки Python та
інші версії не вважаємо перевіреними. Загальна вимога проєкту >=3.11 не є
обіцянкою протестованого Windows-трасування на всьому цьому діапазоні.

| Сценарій | Фактично отримано | Межа |
|---|---|---|
| Python open / відсутній файл | Audit open для обох спроб | Подія не повідомляє результат |
| Відносний шлях / повтори | Збережений raw шлях, дві окремі події | Контрольний cwd, не загальна нормалізація |
| Пробіли / українські символи | Читання та запис шляхів спрацювали | Не всі Windows namespaces |
| Звичайний import | Audit import та спроби .pyc/.py | Не повний startup/cached-import coverage |
| importlib import | Спроби відкриття, без import у цьому тесті | Однієї import-події недостатньо |
| importlib.resources | Відкриття ресурсу, правильний вміст у тесті | Лише пакет-каталог, не ZIP |
| Native CreateFileW/ReadFile | Audit лише ctypes.call_function; ETW Read зіставлений із Create | Не всі нативні бібліотеки/API |
| Два дочірні процеси | ETW Read-кандидати для обох; батьківський audit відкриття не бачив | PID відомі з тесту, не виявлення дерева |
| Path.exists | Немає audit-подій під час двох викликів | ETW-сценарій ще не перевірений |
| listdir/scandir | Відповідні audit-події | ETW-сценарій ще не перевірений |
| Процес + файл в одному capture | Усі контрольні перевірки ProcessStart/Create/Read/Close/ProcessStop пройшли | Один процес, один нативний Read |

Останній ручний capture: 687fab6e1f224e1fbc92a7214b58feac, PID 21036,
creation FILETIME 134367388002971131, sequence 25839. ID доказів:
99 / 5286 / 5330 / 5348 / 5372. Оригінальний ETL лишається в користувача;
цей патч не містить вигаданого JSON, який видається за Windows-запуск.

Для однієї події tracerpt видав 22:26:40.297133000+02:59, Get-WinEvent —
19:26:40.2971330Z. Буквальне прочитання відрізняється рівно на 60 секунд.
Payload CreateTime в обох збігся з API FILETIME. Причину й загальне рішення
ще не встановлено; не віднімати хвилину й не замінювати offset евристикою.

## Межа inventory / що ще не працює

Inventory v1 приймаємо незмінним; власників і захист не переписуємо.
Не порівнюємо normalized_path із inventory path простим рядком. Внутрішній
normcase(resolve(...)) для власників не є погодженим ключем tracer.

Ще немає перевіреного адаптера для регістру/case-sensitive каталогів,
device/extended paths, довгих шляхів, symlinks/junctions/hardlinks, помилок та
заміни файла після capture. Немає довільної scan-команди, загальної кореляції
одночасних операцій, повного дерева процесів, перевіреного абсолютного часу,
повної обробки втрат/переривання й збирання wheel. Цей результат поки НЕ
відповідає критерію готового з'єднання за перевіреним inventory-шляхом.

Наступні зміни — по одній: Windows-перевірка пакетних команд і JSON; узгоджений
path adapter; сценарії й негативні тести; підключення CLI лише за узгодженням.

## Тести

Без Windows-трасування:

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
python -m unittest discover -s tests -p "test_windows_tracing.py" -v
python -m unittest discover -s tests -v
```

Це синтетичні перевірки: XML/Unicode, точна арифметика, PID/sequence,
FileObject reuse, повтори, невідомі втрати, нерозв'язані події, raw-path
provenance, ID capture та збереження JSON. Вони не підміняють Windows-тест.

## Перевірка цієї зміни в sandbox

Python 3.13.14, Linux: 19 нових тестів і всі 40 тестів проєкту пройшли. Синтаксис трьох модулів перевірений. Windows-запуск пакетних команд і wheel не перевірені.
